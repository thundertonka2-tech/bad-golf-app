# Bad Golf — DECLARED LARGE REMOVALS
#
# The stale-base guard (scripts/guard_stale_base.sh, check 4) blocks a commit
# that drops more than 200 net lines from golf-app.html or www/index.html,
# because a big unexplained shrink is the fingerprint of writing from a STALE
# COPY of the file. That check has no general off switch on purpose.
#
# A removal you actually meant to make gets declared here instead:
#
#     <version>        <file>            <max-drop>
#     v2026.11.1449    golf-app.html     400
#
# Why this is safer than `git commit --no-verify`:
#
#   * It is scoped to ONE check on ONE file. Truncation, web/iOS drift, lost
#     symbols and the version check all stay fully armed. --no-verify turns
#     off every one of them, including the truncation checks the guard exists
#     for -- and GitHub Desktop cannot pass --no-verify at all.
#   * The actual drop must fit inside the declared maximum, so an entry cannot
#     quietly cover a bigger loss than the one that was reasoned about.
#   * It is honoured ONLY while that file's own BG_BUILD still equals the
#     version named. It EXPIRES BY ITSELF on the next build. A forgotten entry
#     disarms nothing -- which is the trap a permanent override would set.
#
# Every allowance is printed by the guard when it applies, so a large removal
# can never pass quietly. Old entries are inert and can be left as history or
# deleted, whichever you prefer.
